De la petición a la entrega, con bucles y puertas

Cada caja es un paso; cada rombo es una decisión; cada bucle vuelve al punto donde se puede corregir. El agente propone; la puerta decide; la persona autoriza.

implementado pendiente opcional decisión humana eval aún atada a OpenCode
Fuenteneutral

0. Repos, norma y adaptadores

Cuatro repos separados: dev-agent-kit (puerta), dev-agent-profiles (lenguaje), scalpers-tech-doc (norma y documentación de empresa) y scalpers-v11 (producto). techdoc no es submódulo: ~/.agents/AGENTS.md enlaza su AGENTS.md y check-techdoc.sh comprueba remoto, rama, commit y limpieza. El repo guarda una sola fuente: skills/, commands/ y agents/; los adaptadores se generan y gentle-ai sincroniza los globales.

Artefactos: skills/*/SKILL.md, AGENTS.md, AGENTS.fragment.md, techdoc/AGENTS.md, adapters gitignored
Si check-techdoc falla por remoto, rama o árbol sucio, no se instala perfil ni se da la norma por buena: se cierra en el repo de empresa.

Personanegocio

1. Entrada

Jira SIS, ticket, bug o idea. La persona fija el alcance, la prioridad y lo que no se toca. El agente no inventa el objetivo.

Artefacto: ticket o TASK.md con el resultado esperado

Agenteclasifica

2. ¿Qué tipo de trabajo es?

Bug reproduciblerepro-first: escribe el test que falla, conserva la salida y recién después corrige.
Feature o cambioSDD (spec-driven-development): spec, criterios de aceptación y plan antes de tocar código.
Si no se puede reproducir o el requisito es ambiguo, vuelve a la persona; no adivines.
↓
Perfiluno activo

3. Preparar el entorno

Rama feat/fix/hotfix. Elige el perfil: odoo11 (guard/odoo.sh, verify, skills, casos) o php (esqueleto). Escribe DEV_AGENT_PROFILE en .dev-agent/config. Rellena verify/config.env con base desechable; nunca la base compartida.

Artefactos: profile.json/env, .dev-agent/config, verify/config.env, rama
↓
Agenteimplementa

4. Implementar

Cambio, tests y documentación en el mismo commit. Respeta las reglas del perfil y del núcleo: evidencia, sin secretos, sin producción, sin comentarios de prosa, un cambio un commit.

Artefactos: diff, tests, CHANGELOG, docs
↓
Puertapre-commit

5. Guard: genérico + perfil

El hook ejecuta guard.sh --staged: ruff, black, mypy, eslint, tsc, gitleaks, comment_lint y los checks del perfil. Odoo añade sudo, cr.commit, SQL y print. skipped no es pass: se dice por qué se omitió.

PasaContinúa a verify.
FallaCorrige la causa raíz; no borres el check para ponerlo verde.
↺ Falla → vuelve a implementar → guard otra vez.
Artefacto: guard-report.json
↓
Puertapre-push

6. Verify: comportamiento real

verify/run.sh arranca el entorno, comprueba salud, ejecuta smoke y tests, y escribe evidence/<run-id>/summary.json. El TEST_CMD debe cubrir el cambio; no un smoke de otro módulo. Sin configuración, sale 2: no es verde.

PasaContinúa a la decisión de eval.
FallaCorrige el primer fallo; vuelve a verify.
↺ Falla → implementar → guard → verify.
Artefacto: evidence/<run>/summary.json y logs
↓
Evalsolo si cambia

7. ¿Cambió una skill, prompt, regla o rúbrica?

NoSalta a revisión humana.
SíCaso con TASK.md y context.json; dry-run; K=3 con juez distinto; score.json.

Umbral 8,5. Si baja, mejora la skill y repite; no debilites la rúbrica ni cambies el juez. El juez recibe artefactos, no la narración del agente.

↺ score < 8,5 → editar skill → repetir K=3 → registrar línea base.
Artefactos: score.json, run-*/output.md, docs/EVAL-BASELINE.md
Deuda conocida: evals/harness.py y evals/loop.sh todavía ejecutan OpenCode; el runner neutral está pendiente de revisión.

Personarevisa

8. Revisión humana

Una persona lee el diff, el summary y, si aplica, el score. GGA es consejo opcional; no sustituye a guard/verify. La revisión no se delega al agente que escribió el cambio.

Artefactos: diff revisado, informe de GGA si se usó, comentarios
↓
Repo/CIentrega

9. Rama, MR, CI y merge

Rama y MR con el cambio y la evidencia. El CI del repo es la garantía dura; los hooks se pueden saltar con --no-verify. Si el CI está rojo, se corrige. El merge y el despliegue son decisiones humanas; el kit no despliega.

CI verde + revisiónMerge humano; producción solo con autorización explícita.
CI rojoCorrige y repite; no se fuerza el merge.
Artefactos: MR, pipeline, commit firmado, evidencia adjunta
↓
Memoriaaprende

10. Cerrar el ciclo

engram guarda la decisión o el bug no obvio; el CHANGELOG y la skill recogen la lección. Si el mismo error aparece dos veces, se convierte en lint, test o CI.

Artefactos: entry de engram, CHANGELOG, nueva regla

Qué queda por el camino

  • Contexto: AGENTS.md, AGENTS.fragment.md, skills, commands, agents.
  • Trabajo: TASK.md, spec, test rojo, diff, tests, docs.
  • Puertas: guard-report.json, summary.json, score.json.
  • Entrega: rama, MR, pipeline, revisión humana, autorización de producción.
  • Memoria: engram, CHANGELOG, nueva regla.
La puerta es un comando; el agente es intercambiable. Odoo 11 y PHP viven en dev-agent-profiles, no en el core. Fuente: docs/CREAR-PERFIL.md · docs/DIAGRAMA-SISTEMA.md
