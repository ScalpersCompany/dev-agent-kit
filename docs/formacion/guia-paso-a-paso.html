De la descarga a la primera prueba.

Esta guía sirve para una cosa: que tú puedas enseñar a un compañero, sin improvisar, cómo se descarga el kit, cómo se instala, qué se comprueba después y cómo se demuestra que el sistema funciona. Los comandos están copiados del instalador y del runner actuales. Si algo no se ha ejecutado, se dice; no se pinta de verde.

instalación guiadaCodeGraph + MCP + skillsevidencia antes de “hecho”

Referencias de tecnologías: URL, versión y papel de cada herramienta.

Herramientas de apoyo: Gentle configura agentes y skills; RSC ordena especificación y tareas; RSC Brain (“Brime”) conserva una wiki; Engram recuerda decisiones; CodeGraph explica el código. No son la puerta: qué es cada una y para qué sirve.

Paso 0

Antes de tocar nada.

01

Dónde

En el repo de desarrollo, nunca en producción. Si el repo es compartido, usa una rama y un entorno desechable para las pruebas.

Qué necesitas

bash, git, Python 3, rsync, curl, Node/npm y un agente: Claude Code, OpenCode, Codex, pi o Hermes. El instalador puede poner Engram, GGA, gentle-ai y jq si faltan.

Qué no hará

No despliega, no reinicia servicios, no toca la base compartida, no guarda secretos y no hace push. Los backups quedan como .bak-<fecha>.

La regla que hay que decir en voz alta: “instalado” no es “probado”. La instalación termina con un smoke de toolchain, pero el cambio real se prueba con guard, verify y, si hay UI, E2E.
Paso 1–8

Descargar, instalar y responder al menú.

02

El instalador se puede leer antes de ejecutarlo. Clona el kit en tu home; si no existe el repo de perfiles, lo clona él. Después abre el menú interactivo.

git clone https://github.com/ScalpersCompany/dev-agent-kit.git "$HOME/.dev-agent-kit"
"$HOME/.dev-agent-kit/install.sh"
Repo de desarrollo.

Escribe la ruta del repo donde vas a trabajar. No uses `/`, tu `$HOME` ni el propio kit.

Perfil y perfil activo.

Elige `odoo11` para el trabajo de Odoo 11. Si instalas varios, uno queda activo; los demás quedan disponibles.

Agentes.

Marca Claude Code y/o OpenCode para generar sus adaptadores. Codex, pi y Hermes reciben copias globales. Si usas Claude, el instalador configura también su MCP de Engram.

CodeGraph, Engram y tech-doc.

CodeGraph indexa estructura y llamadas; Engram guarda decisiones; tech-doc enlaza la norma de empresa. Si no tienes acceso a tech-doc, se puede omitir y queda pendiente, no verde.

Confirmar y toolchain.

El instalador muestra el resumen y pide continuar. Después pregunta por la toolchain: Engram, GGA, gentle-ai y Claude si faltan, jq, MCP de Engram y skills globales. Termina con un smoke.

Herramientas de guard.

La siguiente pregunta instala ruff, black, mypy, eslint, tsc y gitleaks. Son opt-in en guard: ruff/black/mypy solo corren si el repo tiene su configuración; eslint/tsc solo si hay package.json/tsconfig; gitleaks y el perfil activo sí se ejecutan.

RLM Agent (opcional).

El instalador pregunta si quieres el kernel Python persistente y el contexto fuera del prompt. No es una puerta de calidad: guard, verify y el flujo team funcionan sin él. Solo cubre Hermes, OpenCode y pi; si usas Claude Code o Codex, se omite. Responde no si no lo necesitas.

E2E y GGA.

E2E pregunta por dependencias npm, Chromium, comando, URL local y health path. GGA instala las reglas del perfil y pregunta por el pre-push. La URL nunca es producción.

Verify ahora.

Si ya tienes un comando de tests o E2E, puedes lanzarlo al final. Si no, se configura después; no se inventa un comando.

Qué significa “global” aquí: el kit y el wrapper se instalan una vez en tu home, y las skills se copian a las rutas globales de los agentes elegidos. Los hooks y la configuración de verify/E2E viven en el repo porque son locales a ese repo.
Paso 4

Los cinco comandos que hay que ejecutar al terminar.

03
dev-agent doctor
dev-agent profile list
dev-agent codegraph
codegraph status "$PWD"
engram ps
engram doctor
claude mcp get engram        # si usas Claude Code
opencode mcp list            # si usas OpenCode
find "$HOME/.claude/skills" -maxdepth 2 -name SKILL.md | wc -l
find "$HOME/.config/opencode/skills" -maxdepth 2 -name SKILL.md | wc -l
ComandoQué debe salirQué no es prueba
dev-agent doctorok para el núcleo; warn para opcionales; FAIL si falta algo obligatorio.Un warn no es un fallo, pero un FAIL no se ignora.
dev-agent profile listEl perfil activo marcado con *.Una lista sin perfil activo no sirve.
dev-agent codegraphÍndice sincronizado; codegraph status lo confirma.Un índice viejo no es contexto actual.

La toolchain se prueba a sí misma: el instalador ejecuta un smoke de binarios, versiones, MCP de Engram, skills y engram doctor. Si ese smoke falla, no sigas a la formación: corrige la instalación.
Paso 5

CodeGraph: del árbol a un mapa consultable.

04

El instalador intenta indexar el repo si CodeGraph está disponible. Si lo omitiste o el índice no existe, hazlo ahora. El agente debe consultar el mapa antes de hacer búsquedas amplias.

cd /ruta/a/tu/repo
if [ ! -d .codegraph ]; then
  codegraph init "$PWD"
else
  dev-agent codegraph
fi
codegraph status "$PWD"
codegraph query "nombre_de_la_clase_o_endpoint"

Qué consigue

Estructura, símbolos, llamadas y blast radius. El agente deja de adivinar por el árbol y consulta el mapa.

Qué no es

No es una puerta de calidad ni sustituye a tests, guard o verify. Un índice desactualizado no es evidencia.

Para enseñarlo: abre codegraph status, muestra un fichero y su llamada, y explica que el contexto se construye antes de editar. Después pide al agente que consulte CodeGraph antes de tocar el código.
Paso 6

La primera puerta: guard y verify.

05
cd /ruta/a/tu/repo
git switch -c feat/prueba-devkit

# 1) un cambio pequeño, con su test y su documentación
# 2) prepara el cambio y pasa el guard
git add <archivo>
bash guard/guard.sh --staged

# 3) revisa la configuración antes de la prueba real
sed -n '1,120p' verify/config.env

# 4) ejecuta la prueba completa
bash verify/run.sh

# 5) lee la evidencia, no solo el código de salida
find evidence -name summary.json -print -exec cat {} \;

0

Todo configurado y ejecutado: el summary dice pass y hay evidencia.

1

Algo falló: se corrige la causa. No se convierte en verde.

2

No hay SMOKE_CMD, TEST_CMD ni E2E_CMD. No es un pass: es una configuración incompleta.

Qué mirar en evidence/<run-id>/: summary.json, los logs, los exit codes y, si hay E2E, e2e/report/ y e2e/test-results/. El chat no es la evidencia.
Paso 7

Si el cambio tiene flujo web, añade E2E.

06

El instalador pregunta si quieres dependencias npm y Chromium, y escribe la configuración. Si dijiste que no, puedes hacerlo ahora. El E2E se ejecuta después de smoke y tests, nunca en producción.

cd /ruta/a/tu/repo
( cd e2e && npm install )
( cd e2e && npx playwright install chromium )
# edita una URL LOCAL en los dos ficheros de configuración
grep -E '^E2E_' verify/config.env .dev-agent/verify.env
bash verify/run.sh
find evidence -path '*/e2e/report/index.html' -print
Un smoke no es un E2E. El smoke comprueba que responde; el E2E recorre un flujo de usuario y deja traza, captura o vídeo del fallo. Si no hay flujo de UI, no inventes uno.
Qué contar al compañero si pregunta por Playwright

El baseline e2e/tests/health.spec.ts solo comprueba que la app responde y renderiza. Las specs de negocio se añaden en e2e/tests/, con selectores de usuario y aserciones sobre el resultado. Los proveedores externos se sustituyen por un fake local o una cassette; la aplicación bajo prueba no se mockea.

Paso 8

GGA: la segunda revisión, no la puerta.

07
cd /ruta/a/tu/repo
bash scripts/review-gga.sh . --blocking --pr-mode --diff-only

# si solo quieres el informe, sin bloquear:
bash scripts/review-gga.sh . --advisory --pr-mode --diff-only

Qué revisa

Las reglas del núcleo más las del perfil activo. Odoo 11 no hereda las reglas de PHP ni al contrario.

Qué no hace

No ejecuta el pipeline, el lint ni los tests: exige su evidencia. No sustituye a guard, verify, CI ni a la revisión humana.

Si GGA falla por falta de proveedor: no es un falso positivo; falta configuración. El instalador deja el proveedor vacío a propósito y el doctor lo avisa. No ejecutes gga install: pisaría el pre-commit del kit.
Cómo enseñarlo

Una sesión de 25 minutos, tres actos.

08
MinutoQué hacesQué ven
0–3Problema y promesa: el agente propone; la puerta comprueba; la persona decide.Una frase, no una lista de herramientas.
3–10Instalación en directo: clonar, menú, toolchain, doctor.El menú real, el smoke y las skills globales.
10–16CodeGraph y contexto: indexar, consultar, explicar una llamada.El mapa antes de editar.
16–22Guard y verify sobre un cambio pequeño.Summary, logs y evidencia; un fallo real si se puede.
22–25GGA y revisión humana; qué queda pendiente.Veredicto y límites; no se promete merge.

Antes de la sesión

Ten un repo desechable, un cambio pequeño, un test que puedas poner en rojo y la URL local de la app. No uses datos de cliente.

Durante

Haz que el compañero escriba los comandos. Tú explicas qué esperar; no dictas la salida.

Al cerrar

Pide que repita el flujo sin ti: rama, cambio, guard, verify, evidencia y revisión. Si no puede, la formación no terminó.

Frase de cierre: “este cambio tiene un test, un summary y un veredicto; lo que falta es esto”. Si no se puede nombrar el artefacto, todavía no está verificado.

Antes de decirlo

Checklist de instalación y primera prueba.

10

Instalación

  • Repo correcto y rama de trabajo.
  • Perfil activo correcto.
  • Toolchain y smoke sin errores.
  • MCP de Engram en el agente que se usa.
  • Skills globales presentes.
  • CodeGraph indexado y sincronizado.
  • Hooks instalados.
  • RLM solo si se pidió: no es requisito de la puerta.

Primera prueba

  • Cambio pequeño con test y documentación.
  • Guard sobre staged.
  • Verify con summary 0.
  • E2E si hay flujo web, con informe y trazas.
  • GGA revisado o fallo explicado.
  • Evidencia localizada; no una captura del chat.
  • Sin push, sin producción, sin secretos.
