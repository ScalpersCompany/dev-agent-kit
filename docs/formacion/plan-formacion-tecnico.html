01 · Formación interna · material del formador

Enseñar el flujo, no la herramienta.

Guía para preparar y conducir la formación de DevAgentKit con el equipo. La presentación de compañeros explica el qué y el porqué; este documento guarda el cómo, los comandos, las demos y lo que no se puede prometer.

4 sesiones propuestas Odoo 11 · PHP 8 · hexagonal guard · verify · E2E producción fuera
02 · Diseño de la formación

Plan de cuatro sesiones

02

Propuesta ajustable. Cada sesión termina con una evidencia observable, no con una explicación. La primera sesión instala y mira; la segunda ejecuta el flujo completo; la tercera discute perfiles y criterio; la cuarta explica el trabajo repartido entre agentes.

SesiónDuraciónObjetivo observableEvidencia de salida
1 · Mapa y primera puerta90 minInstalar en un repo desechable, ejecutar doctor, explicar guard y sus estados.Repo con .dev-agent, guard ejecutado y salida comentada.
2 · Verify y E2E120 minConfigurar verify, ejecutar tests y un flujo Playwright, leer la evidencia y provocar un fallo.summary.json con e2e pass; e2e/report y traza.
3 · Perfiles y GGA90 minElegir perfil, cargar sus reglas GGA, revisar un diff y decidir con evidencia.Diff revisado, reglas del perfil y checklist final.
4 · Equipo y roles60 minRenderizar un agente por rol, explicar el traspaso por referencia y ejecutar team-run en seco.roles.json, roles renderizados, --check y team-run --dry-run.
Regla de pacing: no se avanza a la sesión 2 sin que todos hayan visto un guard real y entiendan que skipped no es verde. En la sesión 2, no se avanza al E2E hasta que verify deje un summary legible.

04 · Antes de empezar

Requisitos y seguridad

04

Entorno

  • Git y terminal; Docker si el repo lo usa.
  • Node 20+ y npm para Playwright.
  • Python 3.8+ para el núcleo y los perfiles.
  • Un repo de desarrollo desechable o una rama de laboratorio.
  • Acceso al repo de perfiles y, si aplica, a tech-doc.

Límites que se dicen en voz alta

  • Nada de producción, bases compartidas ni datos de cliente.
  • Sin tokens ni claves en el repo, la configuración o las capturas.
  • El push, el merge y el release son humanos.
  • El CI de Scalpers no se modifica desde esta formación.
  • Un hook se puede saltar; el CI y la revisión siguen siendo la garantía.
Prerrequisito bloqueante: si falta el proveedor aprobado para GGA, la formación puede explicar el flujo y ejecutar guard/verify, pero no debe fingir una revisión GGA. Se resuelve el acceso o se aplaza esa parte.
05 · Arquitectura

Mapa técnico

05

dev-agent-kit

Contrato neutral: AGENTS, skills, comandos, juez, guard, verify, hooks, evals, e2e, instalador. No contiene Odoo ni PHP.

dev-agent-profiles

Odoo 11, PHP 8, hexagonal y team. Cada perfil aporta guard, verify, skills, evals y su gga/REVIEW-RULES.md.

scalpers-tech-doc

Norma de empresa canónica. Se enlaza en ~/.agents/AGENTS.md; no se copia. El check falla cerrado si el clon no está limpio.

repo-de-desarrollo/
├── AGENTS.md
├── skills/ commands/ agents/ verify/ guard/ evals/
├── e2e/                      Playwright: config, package, tests/
├── .dev-agent/               perfil activo y config local (no se versiona)
├── .git/hooks/pre-commit     guard --staged
└── .git/hooks/pre-push       verify/run.sh

El repo de producto solo recibe el kit y el perfil activo. team no es un perfil de lenguaje: se activa sobre un perfil base y delega en él los checks del lenguaje. El perfil no se convierte en una copia del producto ni la norma se duplica dentro del kit.

06 · Puesta en marcha

Instalación y configuración

06
Clonar el kit y abrir el instalador.

Una línea, sin curl | bash; el instalador se puede leer antes de ejecutar.

Elegir perfil, perfil activo y agentes.

El menú descubre los perfiles; se puede instalar uno, varios o todos. Siempre queda un perfil activo.

Decidir extras.

El instalador pregunta también por Engram, GGA, gentle-ai y Claude: si faltan, los instala, configura el MCP de Engram y copia las skills globales. Después pregunta por las herramientas de guard (ruff, black, mypy, eslint, tsc, gitleaks), CodeGraph, Engram, tech-doc y el harness E2E. Si falta una herramienta opcional, avisa; si falla una obligatoria, para.

Cerrar con doctor.

El doctor separa instalado, opcional y FAIL. Un warn no es verde.

git clone https://github.com/ScalpersCompany/dev-agent-kit.git "$HOME/.dev-agent-kit"
"$HOME/.dev-agent-kit/install.sh"

Para un laboratorio pequeño y no interactivo, el kit también ofrece scripts/bootstrap.sh con --profile y --with-verify; no instala CodeGraph, Engram ni tech-doc si no se piden. No es el camino principal de la formación; sirve para repetir el laboratorio.

bash scripts/bootstrap.sh /ruta/al/repo-desechable --profile odoo11 --with-verify
No copies verify/config.env de tu máquina. El perfil se copia con su ejemplo; la configuración real es local y puede contener rutas o comandos que no sirven en otro entorno.

Procedimiento verificado, de la descarga al primer verify

Comprobar el target.

Entra en el repo de desarrollo, no en producción. Comprueba que es el repo Odoo Doodba y que el árbol está limpio o que sus cambios están identificados.

Descargar el kit.

El clon queda en el home del usuario. No se instala nada en el repo todavía.

Ejecutar el instalador.

Elige perfil odoo11, el perfil activo, los agentes y los extras. El instalador respalda lo que reemplaza y crea .dev-agent/, verify/, hooks y e2e/.

Leer el doctor.

ok es requerido, warn es opcional o pendiente y FAIL es un bloqueo. Un warn no se pinta verde.

Configurar verify.

Rellena el comando de tests del repo y el comando E2E si el cambio tiene UI. No uses la base compartida ni producción.

Ejecutar las puertas.

Primero guard sobre un cambio staged; después verify. La primera vez, verify debe salir 2 si no hay comandos: eso es configuración incompleta, no un pass.

Instalar GGA.

Añade las reglas del perfil y ejecuta la revisión bloqueante. No ejecutes gga install.

Cerrar con evidencia.

Deja summary.json, el informe E2E y el veredicto de GGA. El merge y el push siguen siendo humanos.

# 1. Target: repo de desarrollo, nunca producción
cd /ruta/a/odoo-doodba-template
git status

# 2. Descargar el kit
git clone https://github.com/ScalpersCompany/dev-agent-kit.git "$HOME/.dev-agent-kit"

# 3. Instalador principal: pregunta y ejecuta cada pieza
#    (toolchain Engram/GGA/gentle/Claude, MCP, skills, E2E, Chromium, GGA y verify)
DEV_AGENT_PROFILES="$HOME/dev-agent-profiles" \
  bash "$HOME/.dev-agent-kit/install.sh" \
  --target /ruta/a/odoo-doodba-template \
  --profiles odoo11 --active odoo11 \
  --agents claude,opencode

# 4. Doctor; los warn son opcionales, los FAIL bloquean
~/.local/bin/dev-agent doctor
~/.local/bin/dev-agent profile list
# si el wrapper no está en PATH:
# "$HOME/.dev-agent-kit/bin/dev-agent" doctor

# 5. El instalador ya escribe la configuración de E2E y de verify.
#    Revisa las rutas y comandos antes de ejecutar la primera puerta:
sed -n '1,120p' verify/config.env
# si no configuraste E2E o tests en el asistente, edita ahora los comandos reales
# (nunca la base compartida ni producción).

# 6. Primera puerta
git add 
bash guard/guard.sh --staged

# 7. GGA: el instalador ya copió las reglas del perfil y, si dijiste que sí,
#    dejó el pre-push preparado. La revisión se lanza aparte:
bash scripts/review-gga.sh . --blocking --pr-mode --diff-only

# 8. E2E: el instalador ya instaló npm/Chromium y escribió E2E_CMD/E2E_BASE_URL.
#    Solo faltan las specs del flujo real; ejecuta:
bash verify/run.sh
Checkpoint real de la formación: el instalador termina con un smoke de toolchain (binarios, MCP de Engram y skills) y con el doctor; no confundas ese smoke con verify. El doctor termina con núcleo correcto; los warn son opcionales o pendientes; profile list marca * odoo11; los hooks existen; y si no configuras ningún comando, verify sale 2. Si configuras E2E sin servidor o sin specs, saldrá 1; eso no es un pass. Un guard sin staged puede imprimir guard: passed con comments skipped: no es una prueba del cambio.
Ejemplo de TEST_CMD para Odoo 11 en Doodba

El comando de test no se inventa: se toma del repo y se ejecuta contra una base desechable. Este ejemplo está documentado en el perfil; cambia el módulo y la base por los del cambio.

DB="test_devkit_verify_$(date +%Y%m%d_%H%M%S)"
docker compose -f devel.yaml run --rm --entrypoint odoo odoo \
  --config=/opt/odoo/auto/odoo.conf -d "$DB" \
  -i scalpers_partner_vat_unique --stop-after-init --workers=0 --log-level=info
docker compose -f devel.yaml run --rm --entrypoint odoo odoo \
  --config=/opt/odoo/auto/odoo.conf -d "$DB" \
  -u scalpers_partner_vat_unique --test-enable --stop-after-init --workers=0 --log-level=test

En verify/config.env, guarda ese bloque como TEST_CMD o llámalo desde un script del repo. El --entrypoint odoo evita el entrypoint de Doodba que falla si los enlaces de addons ya existen. No uses la base scalpers compartida ni producción.

07 · Operación

Flujo diario

07

1 · Contexto

Leer AGENTS y el fragmento del perfil; abrir la skill que corresponde. El agente no improvisa el proceso.

2 · Reproducir

Bug: test rojo primero. Feature: criterio de aceptación antes de escribir. Sin esto, no hay verificación real.

3 · Implementar

Código, tests y documentación en el mismo cambio. Sin comentarios de prosa; docstrings, help y README son documentación.

4 · Guard

Comprueba lo staged: perfil, comentarios y checks del lenguaje. Es rápido; no es la prueba completa.

5 · Verify

Arranca, comprueba salud, ejecuta smoke, tests y E2E; deja evidencia por commit.

6 · Revisión

Una persona lee el diff y la evidencia. GGA es la segunda revisión cuando se ejecuta; no decide el merge.

git switch -c feat/mi-cambio
bash guard/guard.sh --staged
bash verify/run.sh
git add .
git commit -m "feat: ..."

El pre-commit ejecuta guard; el pre-push ejecuta verify con .dev-agent/verify.env. Si no hay TEST_CMD ni E2E_CMD, el hook falla cerrado. --no-verify salta el hook local, no el CI.

08 · Evidencia

Verify y E2E con Playwright

08

Verify es la prueba de comportamiento. El E2E no es un smoke: empieza en la entrada pública, recorre el flujo real y comprueba el resultado visible o persistido. El kit trae el baseline; cada cambio añade su spec.

Qué ejecuta

  • BOOT_CMD y HEALTH_URL si están configurados.
  • SMOKE_CMD.
  • TEST_CMD.
  • E2E_CMD, después de los tests.

Qué deja

  • evidence/<run-id>/summary.json con e2e.
  • e2e/report/index.html y junit.xml.
  • e2e/report/results.json.
  • e2e/test-results/ con trazas, capturas o vídeos de fallo.
El instalador ya hace la parte de instalación. Pregunta si quieres dependencias npm y Chromium, y escribe E2E_CMD, E2E_BASE_URL y E2E_HEALTH_PATH en verify/config.env y en .dev-agent/verify.env. Lo que no puede adivinar es la URL real de tu aplicación ni las specs de negocio: esos dos datos son tuyos.
# Si en el asistente dijiste que sí, esto ya está hecho.
# Para repetirlo a mano:
( cd e2e && npm install )
( cd e2e && npx playwright install chromium )
# Revisa y ajusta la URL local en ambos ficheros:
grep -E '^E2E_' verify/config.env .dev-agent/verify.env
bash verify/run.sh
Pieza¿La instala el instalador principal?Qué queda manual
Harness PlaywrightSí: e2e/ y el scriptAñadir las specs del flujo real.
Dependencias npm y ChromiumSí, si respondes que síConfirmar que hay red; el instalador no instala en silencio.

Un smoke no es un E2E. Un test que se salta, que no se descubre o que no deja artefacto no es evidencia. Si el cambio toca una UI o un flujo de usuario, GGA bloqueará sin la suite y su reporte.

El baseline e2e/tests/health.spec.ts solo comprueba que la aplicación responde y renderiza. Las specs de negocio se escriben en e2e/tests/, con selectores de usuario y aserciones sobre el resultado. No se mockea la aplicación bajo prueba; los proveedores externos usan un fake local o una cassette.

09 · Criterio

GGA por perfil

09

El núcleo aporta reglas agnósticas. El perfil activo añade su gga/REVIEW-RULES.md y el instalador compone ambos. Odoo no hereda las reglas de PHP ni al contrario.

PerfilQué añade a GGAQué no puede hacer
odoo11Manifest y versión, CHANGELOG/README, flake8, pylint obligatorio, check-xml, pipeline, OCA/ORM, seguridad, migraciones, colas y patrones de MR reales.No ejecuta el pipeline ni el lint; exige la evidencia del SHA de cabeza.
phpStrict types, PSR-12, PHPStan, PHPCS, PHPUnit, Composer, seguridad de aplicación y E2E.El perfil sigue siendo esqueleto: sus checks de guard no están cableados todavía.
hexagonalDominio puro, contrato primero, idempotencia, resultados del proveedor, problem+json, persistencia, tests, Docker y E2E.No puede demostrar un flujo de negocio que no exista como spec.
teamCoordinación multiagente: plan, dev, review, verify y judge; superficie de escritura, traspaso por referencia, roles de solo lectura y evidencia. Delega el lenguaje en el perfil base.No es un perfil de lenguaje y no sustituye al perfil base.
 
# El instalador principal ya copió las reglas del perfil y preguntó por el pre-push.
# Para rehacerlo a mano:
bash scripts/install-gga.sh . --profile "$HOME/dev-agent-profiles/profiles/odoo11"
bash scripts/review-gga.sh . --blocking --pr-mode --diff-only
# opcional: bloquear también el pre-push
bash scripts/install-gga.sh . --profile "$HOME/dev-agent-profiles/profiles/odoo11" --with-pre-push
GGA no es la puerta determinista. Guard y verify son la puerta; GGA es la segunda revisión semántica. No se ejecuta gga install: pisaría el pre-commit del kit.

Trabajo repartido

El perfil team fija quién escribe, quién revisa y quién verifica. Los roles se generan desde roles.json; el contrato es la fuente de verdad y --check detecta un agente atrasado.

dev-agent roles claude --check
dev-agent roles opencode --check
.dev-agent/profiles/team/bin/team-run.sh . --spec odd/tasks/<feature>.md --dry-run
10 · Aula

Demos, fallos deliberados y preguntas

10

Demo 1 · Instalación y doctor

Repo desechable, instalación, perfil activo y doctor. Pregunta: ¿qué señal es warn y por qué no es verde?

Demo 2 · Guard y verify

Comentario de prosa staged → guard falla; config vacía → verify sale 2; config real → summary y e2e pasan.

Demo 3 · E2E con fallo

Cambiar una aserción o apuntar a una ruta inexistente; abrir el HTML, la traza y la captura. Pregunta: ¿qué falta para que sea evidencia?

Demo 4 · GGA

Instalar reglas del perfil, revisar un diff y leer un hallazgo. Pregunta: ¿qué puede comprobar GGA y qué debe venir del pipeline?

# Fallo deliberado 1: comentario de prosa
printf '# esto explica el cambio\n' >> ejemplo.py
git add ejemplo.py
bash guard/guard.sh --staged

# Fallo deliberado 2: verify sin configuración
printf 'TEST_CMD=""\nE2E_CMD=""\n' > verify/config.env
bash verify/run.sh   # exit 2, no es verde

# Fallo deliberado 3: E2E que no llega
E2E_BASE_URL="http://127.0.0.1:9" bash verify/run.sh
# leer evidence/<run-id>/e2e/report y test-results

Después de cada fallo, el formador pregunta qué artefacto falta y qué se podría afirmar sin él. La respuesta correcta nunca es “lo he probado en local”.

11 · Cierre

Evaluación y checklist

11

El alumno sabe…

  • Explicar qué es el kit y qué no es.
  • Instalar en un repo desechable y leer doctor.
  • Distinguir skipped, exit 2, FAIL y PASS.
  • Configurar verify y ejecutar un E2E.
  • Leer summary y e2e/report.
  • Elegir perfil y explicar por qué GGA es por perfil.
  • Decir qué falta cuando no hay evidencia.

Evidencias mínimas

  • Salida de guard sobre un cambio staged.
  • Summary con tests y e2e en pass.
  • HTML/JUnit/JSON y traza de un fallo.
  • Diff revisado con un hallazgo GGA.
  • Checklist de límites y seguridad.
No se evalúa una presentación: se evalúa una ejecución con salida real. Un alumno que no puede mostrar el summary no ha completado la sesión.
12 · Realidad

Problemas frecuentes y límites

12
El instalador no encuentra perfiles

Comprueba DEV_AGENT_PROFILES o clona dev-agent-profiles. El instalador intenta clonarlo; si no hay acceso, el núcleo puede seguir sin perfil, pero no lo presentes como instalación completa.

Guard dice skipped

No hay staged o falta el perfil activo. No es un pass. Para la demo, stagea un fichero y ejecuta bash guard/guard.sh --staged.

Verify sale 2

No hay SMOKE_CMD, TEST_CMD ni E2E_CMD. Rellena la configuración local; no la copies de otra máquina.

Playwright no arranca

Falta npm install o npx playwright install chromium. Comprueba E2E_BASE_URL antes de culpar al test. El fallo debe dejar traza y captura.

El hook no ve la configuración

El pre-push usa .dev-agent/verify.env, no verify/config.env. Si usas una GUI de git, puede no heredar variables de entorno; exporta DEV_AGENT_KIT o usa la terminal.

El perfil PHP no está cableado

El perfil y sus reglas GGA existen, pero PHPStan/PHPCS/PHPUnit en guard siguen pendientes. No presentes el perfil como completamente operativo.

GGA no puede ver el pipeline

GGA lee el diff y la evidencia; no ejecuta git, lint ni CI. Debe exigir el pipeline id y estado del SHA de cabeza. Si no están, no es PASS.

El E2E es solo el baseline

health.spec.ts no es la suite completa. Cada flujo de usuario necesita su spec; GGA bloquea una UI sin ella.

Límites que se dicen: el CI de producto no se toca; el push/merge/release son humanos; el kit no despliega; el hook se puede saltar; un warn no es verde.
