Formación interna · guía del participante

Saber qué tienes entre manos.

Una guía para entender las piezas que usamos todos los días: qué es una skill, para qué existe un juez separado, qué aporta un perfil y cómo encajan en un cambio real. No es un manual de comandos: es el mapa para que las conversaciones empiecen en el mismo sitio.

01 · El mapa

Cuatro repos, tres capas y una puerta.

01

dev-agent-kit

El contrato neutral: skills, comandos, juez, guard, verify, hooks, evals, e2e e instalador. No contiene Odoo ni PHP.

dev-agent-profiles

El dominio: Odoo 11, PHP 8, hexagonal y el flujo team. Cada perfil añade guard, verify, skills, evals y GGA. RLM Agent es un extra opcional del instalador, no un perfil.

scalpers-tech-doc

La norma de empresa. Se enlaza, no se copia. Si el clon no está limpio, el check falla cerrado.

La puerta no es un agente. Guard y verify son comandos; GGA es una segunda revisión; el juez evalúa skills. El agente es la herramienta que usas, no la garantía.
02 · Skills

Una skill es un procedimiento que se puede repetir.

02

No es un prompt suelto ni una colección de frases. Es un fichero SKILL.md con un nombre, una descripción que dice cuándo usarlo y una secuencia de pasos que termina en una salida verificable. El agente la lee; tú puedes leerla y discutirla.

Anatomía

  • name: identificador corto.
  • description: cuándo se usa y qué produce.
  • Cuerpo: pasos, criterios de salida, fallos y formato del informe.
  • references/, scripts/ y templates/ cuando hacen falta.

Dónde vive

  • skills/ del kit: las cinco core.
  • profiles/<perfil>/skills/: las del dominio.
  • Adaptadores generados en .claude/skills y .opencode/skills.
  • La fuente es la del kit o el perfil; los adaptadores no se editan a mano.

# ver la fuente de una skill
sed -n '1,80p' skills/dev-verify/SKILL.md

# regenerar los adaptadores del repo
bash scripts/install-agent-adapters.sh . --agents claude,opencode \
  --profile "$HOME/dev-agent-profiles/profiles/odoo11"
Regla de oro: si una skill no termina en un comando, un fichero o un veredicto, es una opinión. Una skill se mejora cuando un fallo real muestra que le falta un paso; no se reescribe porque suene mejor.
Perfil ≠ skill. La skill dice cómo hacer una tarea; el perfil dice qué significa hacerlo bien en ese stack.
03 · Perfiles

El perfil pone el lenguaje; el núcleo pone la puerta.

03

El kit no sabe Odoo ni PHP. Un perfil declara el lenguaje, sus checks, sus skills y sus reglas GGA. El repo tiene un perfil activo; las reglas de un stack no se heredan en otro.

Qué contiene

  • profile.json y profile.env.
  • guard/ y verify/.
  • skills/ y evals/.
  • gga/REVIEW-RULES.md: las reglas de revisión del perfil.

Cómo se usa

  • El instalador pregunta qué perfil o perfiles instalar.
  • El activo queda en .dev-agent/config.
  • dev-agent profile list y dev-agent profile use <nombre>.
  • No mezcles reglas de Odoo con PHP o hexagonal.

El perfil activo es uno. Puedes instalar varios, pero no se aplican a la vez. Si guard dice profile: skipped, no hay perfil activo o falta su carpeta: no es un pass.
04 · Juez

El que ejecuta no se pone las notas.

04

El juez es un evaluador separado que lee una rúbrica, la salida de otro agente y los artefactos de la ejecución. Devuelve un JSON con una nota por criterio; el harness calcula la media ponderada y decide si la skill pasa.

Cómo funciona

  • agents/judge.md es el prompt estricto; solo devuelve JSON.
  • evals/harness.py ejecuta K copias en un entorno desechable.
  • El baseline usa K=3 y umbral 8,5; el rubric manda.
  • El juez debe ser un modelo distinto del que ejecutó la skill.

Qué no es

  • No es GGA: GGA revisa un diff; el juez puntúa una skill.
  • No es el CI: el CI ejecuta el repo; el juez mide el comportamiento de la skill.
  • No se ejecuta en cada commit.
  • No convierte una media alta en una aprobación humana.
python3 evals/harness.py \
  --case-dir evals/cases/dev-verify/01-fix-failing-test \
  --rubric evals/rubric.dev-verify.json \
  --agent opencode --model <modelo-aprobado> \
  --judge-agent opencode --judge-model <modelo-aprobado-distinto> \
  --k 3

# validar el caso sin gastar modelo
python3 evals/harness.py \
  --case-dir evals/cases/dev-verify/01-fix-failing-test \
  --rubric evals/rubric.dev-verify.json --dry-run
Qué mirar: el score.json con la media, el umbral, el juez y las razones. Un timeout o un error del ejecutor no es una nota baja: es una evaluación inválida. Una corrida aislada no demuestra una skill; el K y las razones sí.
05 · Agentes

Una fuente, varios clientes.

05

OpenCode, Claude Code, Codex, pi y Hermes no tienen que usar el mismo formato. El kit mantiene una fuente neutral y genera los adaptadores que cada uno lee. Cambiar de agente no cambia el contrato.

Lo neutral

  • AGENTS.md, skills/, commands/, agents/.
  • El juez y el runner neutral.
  • La puerta son comandos de shell y Python.

Lo generado

  • .claude/, .opencode/ y las copias globales.
  • No se editan: se regeneran desde la fuente.
  • dev-agent roles genera un agente por rol desde roles.json; está en rama local.
Roles: el perfil team separa plan, dev, review, verify y judge. La revisión y la verificación trabajan sobre una copia y demuestran que el árbol no cambió; el juez no se puntúa a sí mismo. No está en main: se explica como propuesta hasta integrarlo.
06 · El flujo

Qué se ejecuta y cuándo.

06

Cambio normal

Skill → guard → verify → E2E si hay UI → revisión humana. GGA es la segunda revisión del diff. El juez no entra aquí.

Cambio de skill

Se escribe o modifica la skill, se ejecuta el caso con --dry-run, luego K=3 con juez separado. Se compara con el baseline.

Entrega

El hook local y el CI son compuertas; el push, el merge y el release son humanos. La evidencia es el summary, el informe E2E y el veredicto.

dev-agent guard
dev-agent verify
dev-agent review-gga
# solo si cambias una skill o su rubric
python3 evals/harness.py \
  --case-dir evals/cases/dev-verify/01-fix-failing-test \
  --rubric evals/rubric.dev-verify.json --dry-run
La frase que hay que poder decir: “este cambio tiene un test, un E2E cuando aplica, un summary y un veredicto; lo que falta es esto”. Si no se puede nombrar el artefacto, todavía no está verificado.

08 · Para practicar

Tres ejercicios para comprobar que se entiende.

08

Leer una skill

Abre skills/repro-first/SKILL.md y señala sus pasos, su salida y el fallo que evita. ¿Qué cambiarías si un bug se repite?

Separar juez y GGA

Explica en dos frases qué evalúa cada uno y por qué no se sustituyen. ¿Qué evidencia produce cada uno?

Elegir perfil

Un repo Odoo con vistas y XML, otro PHP sin checks cableados y un microservicio hexagonal. ¿Qué perfil activas en cada uno y qué queda pendiente?

Pregunta de cierre: si alguien dice “está hecho, lo he probado”, ¿qué tres artefactos le pides antes de aceptar el cambio?

Para el paso a paso: abre guía de instalación, CodeGraph y primera prueba.

Referencias: tecnologías, URL oficial y versiones.
