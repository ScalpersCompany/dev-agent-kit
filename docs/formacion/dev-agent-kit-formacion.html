La promesa

Al terminar, no sabrás “usar el kit”.
Sabrás entregar un cambio que se pueda comprobar.

Instalar

Clonar el kit, los perfiles y tu repo; dejarlo en la raíz.

Entregar

Usar skills, modelos aprobados y revisión humana; sin secretos ni producción.

Sesión 1 · lunesPrimero la puerta; después el agente.
Marco mental

Qué es DevAgentKit y qué no es.

Es

  • Una puerta determinista: guard y verify.
  • Un conjunto de skills que el agente lee.
  • Un contrato de perfiles por lenguaje.
  • Una forma de dejar evidencia antes de decir “hecho”.

No es

  • Un modelo ni un proveedor de IA.
  • Un CI remoto ni un sustituto del CI.
  • Un repo de producto fijo.
  • Un auto-merge ni un despliegue.
El agente es intercambiable; la puerta es un comando.
Sesión 1 · lunesHecho ≠ verificado ≠ aprobado.

Descarga

Dos clones y tu repo de desarrollo.

# kit y perfiles mkdir -p "$HOME/dev" git clone https://github.com/ScalpersCompany/dev-agent-kit.git "$HOME/dev-agent-kit" git clone https://github.com/ScalpersCompany/dev-agent-profiles.git "$HOME/dev-agent-profiles" # tu repo de desarrollo, con tu URL y tu credencial git clone <url-de-tu-repo> /ruta/a/tu/repo # los hooks buscan el kit aquí export DEV_AGENT_KIT="$HOME/dev-agent-kit"
Necesitas acceso a los repos de ScalpersCompany; el tuyo, con tu credencial. Nunca pegues un token en un fichero del repo.
Sesión 1 · lunesDEV_AGENT_KIT es el contrato de ruta con los hooks.
Instalación

El bootstrap copia la puerta y los hooks.

cd /ruta/a/tu/repo bash "$HOME/dev-agent-kit/scripts/bootstrap.sh" . --with-verify

Hace

  • Copia AGENTS, skills, commands, agents, verify, guard, evals, scripts, docs y profiles/ (plantilla).
  • Respalda lo existente como .bak-<fecha>.
  • Crea verify/config.env.
  • Instala pre-commit y, con --with-verify, pre-push.

No hace

  • No instala el perfil Odoo o PHP.
  • No crea la base de datos.
  • No configura el modelo.
  • No empuja ni despliega.
El bootstrap sobrescribe AGENTS.md y hace merge de directorios; revisa los .bak. No instala el perfil.
Sesión 1 · lunesBackups primero; nada se borra.
Perfil

Un perfil activo por repo.

mkdir -p .dev-agent/profiles rsync -a --exclude='verify/config.env' \ "$HOME/dev-agent-profiles/profiles/odoo11/" .dev-agent/profiles/odoo11/ printf 'DEV_AGENT_PROFILE=odoo11\n' > .dev-agent/config

Odoo 11

guard/odoo.sh, odoo_lint, verify, tres skills y casos.

PHP

Esqueleto: contrato y plantilla; PHPStan/PHPCS/PHPUnit aún no cableados.

Si guard dice “profile skipped”, no hay config o la ruta no existe. .dev-agent es local; para CI o equipo, copia el perfil a profiles/. Skipped no es pass.
Sesión 1 · lunesEl perfil aporta el lenguaje; el núcleo no sabe Odoo ni PHP.
Verify

Dos ficheros, una idea: comportamiento real.

verify/config.env

Lo usa bash verify/run.sh a mano.

SMOKE_CMD y TEST_CMD.

.dev-agent/verify.env

Lo usa el hook pre-push.

Debe tener el mismo TEST_CMD real.

SMOKE_CMD='python3 -c "import mi_paquete"' TEST_CMD='python3 -m unittest discover -v'
Si no hay SMOKE_CMD ni TEST_CMD, verify sale 2. No es verde: es una configuración incompleta.
Sesión 1 · lunesUna base desechable; nunca la compartida ni producción.
Hooks

La puerta local no es la única puerta.

HookQué ejecutaQué significa
pre-commitguard --stagedSolo lo que entra en el commit; rápido y determinista.
pre-pushverify con .dev-agent/verify.envFalla cerrado si falta el TEST_CMD o la config.
--no-verifysalta el hook localNo salta el CI ni la revisión; no es una salida.
El CI de Scalpers no se toca. El CI del repo y la revisión humana son la garantía dura. Un skipped no es un pass.
Sesión 1 · lunesGuard y verify dejan evidencia; el hook solo la exige.

Sesión 2 · martesDocumentación al final; primero el mecanismo.
Modelos

El kit no elige el modelo; la empresa sí.

Reglas

  • Proveedor y modelo aprobados.
  • Claves en el entorno o gestor del agente.
  • Nunca en el repo, la config o una captura.
  • El juez es distinto del ejecutor.

Práctica

  • Claude: /model, /effort, /context, /cost.
  • OpenCode, Codex, pi, Hermes: su configuración.
  • Eval: <modelo-aprobado> y <modelo-aprobado-distinto>.
  • Primero --dry-run; después K=3.
Una media alta con una corrida baja es una skill inestable. No se declara verde por la media sola.

Eval

Medir una skill, no un cambio de producto.

python3 evals/harness.py \ --case-dir evals/cases/dev-verify/01-fix-failing-test \ --rubric evals/rubric.dev-verify.json \ --agent build \ --model <modelo-aprobado> \ --judge-model <modelo-aprobado-distinto> \ --k 3

Qué hace

  • Worktree o copia desechable.
  • Juez con artefactos.
  • Media, dispersión, tokens y coste.
  • Umbral 8,5.

  • El harness y loop.sh todavía usan OpenCode.
  • El runner neutral está pendiente.
  • No es una puerta obligatoria todavía.

Norma de empresa

tech-doc es la fuente; el kit no la copia.

Su AGENTS.md es la norma canónica. Se enlaza en ~/.agents/AGENTS.md y se comprueba con el script del kit.

git clone git@github.com:ScalpersCompany/scalpers-tech-doc.git \ "$HOME/odoo-doodba-template/scalpers-tech-doc" mkdir -p "$HOME/.agents" ln -sfn "$HOME/odoo-doodba-template/scalpers-tech-doc/AGENTS.md" \ "$HOME/.agents/AGENTS.md" bash "$HOME/dev-agent-kit/scripts/check-techdoc.sh" \ --path "$HOME/odoo-doodba-template/scalpers-tech-doc" \ --branch main --require-link

Regla

  • No es un submódulo.
  • No se copia dentro del perfil.
  • Si el árbol está sucio, el check falla cerrado.
  • --allow-dirty solo para revisión local.
  • El kit no empuja tech-doc.
Sesión 3 · juevesSi no hay acceso a tech-doc, se practica con el AGENTS local; en empresa gana tech-doc.
