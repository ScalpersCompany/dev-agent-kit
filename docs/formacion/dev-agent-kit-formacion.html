Marco mental

Qué es DevAgentKit y qué no es.

Es

  • Una puerta determinista: guard y verify.
  • Un conjunto de skills que el agente lee.
  • Un contrato de perfiles por lenguaje.
  • Una forma de dejar evidencia antes de decir “hecho”.

No es

  • Un modelo ni un proveedor de IA.
  • Un CI remoto ni un sustituto del CI.
  • Un repo de producto fijo.
  • Un auto-merge ni un despliegue.
El agente es intercambiable; la puerta es un comando.

Instalación

Una línea. Después, el menú hace las preguntas.

git clone https://github.com/ScalpersCompany/dev-agent-kit.git "$HOME/.dev-agent-kit" \ && "$HOME/.dev-agent-kit/install.sh"

Qué pasa

  • Preflight de git, Python, rsync y repo.
  • Clona el kit y los perfiles; no toca el repo destino hasta confirmar.
  • Pregunta perfil, perfil activo, agentes y extras.
  • Respalda lo que reemplaza y termina con doctor.

Qué no pasa

  • No se usa curl | bash.
  • No se pide ni se guarda un token.
  • No se copia el HTML privado de tech-doc.
  • No se hace push ni se toca producción.
Si ya tienes el kit clonado: ./install.sh. La misma orden sirve para cualquier repo de desarrollo.

Verify

Dos ficheros, una idea: comportamiento real.

verify/config.env

Lo usa bash verify/run.sh a mano.

SMOKE_CMD y TEST_CMD.

.dev-agent/verify.env

Lo usa el hook pre-push.

Debe tener el mismo TEST_CMD real.

SMOKE_CMD='python3 -c "import mi_paquete"' TEST_CMD='python3 -m unittest discover -v'
Si no hay SMOKE_CMD ni TEST_CMD, verify sale 2. No es verde: es una configuración incompleta.

Hooks

La puerta local no es la única puerta.

HookQué ejecutaQué significa
pre-commitguard --stagedSolo lo que entra en el commit; rápido y determinista.
pre-pushverify con .dev-agent/verify.envFalla cerrado si falta el TEST_CMD o la config.
--no-verifysalta el hook localNo salta el CI ni la revisión; no es una salida.
El CI de Scalpers no se toca. El CI del repo y la revisión humana son la garantía dura. Un skipped no es un pass.
Sesión 1 · lunesGuard y verify dejan evidencia; el hook solo la exige.
Contexto y memoria

CodeGraph y Engram: el repo y la decisión, fuera del chat.

CodeGraph

Indexa estructura, símbolos y llamadas. El agente consulta el repo en vez de adivinar.

codegraph init . codegraph sync . codegraph status .

Engram

Guarda decisiones, bugs y contexto del proyecto. La memoria no se pierde al cerrar la sesión.

engram save "Decisión" \ "Qué y por qué" --type decision
Son contexto, no puertas. Si faltan, el doctor lo dice; no se declara verde lo que no se comprobó.
Sesión 1 · lunesEl instalador los activa si están; el wrapper los usa desde el repo.
Doctor

El cierre no es “instalado”: es “sé qué quedó”.

EstadoQué significaQué hace el formador
okLa pieza está y se puede usar.La enseña como parte del flujo.
warnOpcional o pendiente: CodeGraph, Engram, HTML, TEST_CMD.Explica el límite; no lo pinta de verde.
FAILFalta una pieza obligatoria: git, perfil, hooks.Para y corrige antes de seguir.
dev-agent doctor
El instalador termina con doctor. Si el formador no puede explicar un warn, no lo ha entendido.

Modelos

El kit no elige el modelo; la empresa sí.

Reglas

  • Proveedor y modelo aprobados.
  • Claves en el entorno o gestor del agente.
  • Nunca en el repo, la config o una captura.
  • El juez es distinto del ejecutor.

Práctica

  • Claude: /model, /effort, /context, /cost.
  • OpenCode, Codex, pi, Hermes: su configuración.
  • Eval: <modelo-aprobado> y <modelo-aprobado-distinto>.
  • Primero --dry-run; después K=3.
Una media alta con una corrida baja es una skill inestable. No se declara verde por la media sola.
