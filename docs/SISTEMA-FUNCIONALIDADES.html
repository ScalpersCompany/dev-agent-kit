La idea

El agente propone. La puerta comprueba. La persona decide. El kit conecta esas tres cosas con un contrato común y evidencia local.

01 · Marco
qué es y qué no es

Una puerta de calidad para el desarrollo, no un sustituto del criterio.

DevAgentKit es un conjunto de scripts, skills, perfiles y hooks que se instalan en la raíz de un repo. Hace que el trabajo de cualquier agente pase por comprobaciones deterministas y deje evidencia antes de llegar a revisión.

SÍ

Es

  • Una puerta local: guard y verify.
  • Un contrato de perfiles por lenguaje.
  • Skills que el agente lee como procedimiento.
  • Un instalador que deja el repo listo.
  • Una forma de conservar contexto y decisiones.
NO

No es

  • Un modelo ni un proveedor de IA.
  • Un CI remoto ni un auto-merge.
  • Un repo de producto fijo.
  • Un despliegue ni una herramienta de producción.
  • Una excusa para saltarse la revisión humana.
La regla: hecho no es verificado; verificado no es aprobado. El kit hace visible la diferencia.
02 · Arquitectura
cuatro repos, un contrato

Las piezas están separadas para que ninguna arrastre a las demás.

01 · KIT

dev-agent-kit

Núcleo agnóstico: guard, verify, hooks, skills, comandos, juez, evals, instalador y doctor.

02 · PERFILES

dev-agent-profiles

Contratos por lenguaje. Hoy: Odoo 11 y PHP. El instalador descubre los que existan.

03 · NORMA

scalpers-tech-doc

Documentación y reglas de empresa. Su AGENTS.md es la fuente canónica; se enlaza, no se copia.

04 · DESTINO

tu repo

Odoo, PHP o cualquier stack. Aquí se instala el kit y se activa un perfil.

El kit no incluye Odoo ni PHP. El perfil aporta el dominio; el núcleo solo sabe ejecutar una puerta y leer un contrato.

Adaptadores

Claude Code, OpenCode, Codex, pi y Hermes leen la misma fuente neutral; el proyecto genera sus copias o usa las globales.

Contexto

CodeGraph indexa el repo. Engram guarda decisiones y memoria. Son apoyo, no puertas.

Evidencia

Verify deja salida y resumen. La revisión y el merge siguen siendo humanos.

03 · Autoinstalación
una línea, después un menú

El instalador no es un daemon: es un script que se puede leer y repetir.

Clona el kit, ejecuta install.sh y responde. El script hace el resto; si algo es opcional y falta, avisa y sigue. Si falta una pieza obligatoria, para antes de tocar el repo.

# modo interactivo ./install.sh # modo automatizado, sin preguntas ./install.sh --target /ruta/al/repo --profiles all --active odoo11 \ --agents all --with-codegraph --with-engram --with-techdoc --yes

Qué decide el instalador

  • El repo destino no puede ser /, $HOME ni el propio kit.
  • Respalda lo que reemplaza como .bak-<fecha>.
  • Ajusta la ruta del kit en los hooks instalados.
  • Enlaza dev-agent en ~/.local/bin si puede.
  • Es idempotente: se puede repetir.

Qué no decide

  • No crea la base de datos ni configura Odoo.
  • No elige proveedor ni modelo.
  • No guarda claves ni tokens.
  • No hace push, merge ni despliegue.
  • No borra datos ni historial.

05 · La puerta
lo determinista antes de lo opinable

Guard mira el cambio; verify ejecuta el comportamiento; el hook exige ambos.

guard

Comprueba el cambio: perfil, comentarios nuevos, checks del lenguaje y reglas del repo. Rápido y local.

→

verify

Ejecuta smoke y tests reales con un límite. Deja salida y resumen en la evidencia.

→

hooks

pre-commit ejecuta guard sobre lo staged; pre-push ejecuta verify con la configuración del repo.

→

persona

Revisa el diff, la evidencia y el veredicto. Decide el merge; el kit no lo hace.

skipped

La comprobación no miró nada: no hay perfil activo o no hay ficheros staged. No es un pass.

exit 2

Falta configuración, por ejemplo TEST_CMD. Tampoco es un pass: es una puerta incompleta.

--no-verify

Salta el hook local, no el CI ni la revisión. La garantía dura sigue fuera del hook.

# comprobar a mano dev-agent guard dev-agent verify # la evidencia queda en el repo evidence/<run-id>/summary.json # y .git/dev-agent-evidence/ en el hook
06 · Perfiles
el lenguaje vive fuera del núcleo

Un perfil activo por repo; el resto quedan disponibles.

ODOO 11

Odoo 11

Guard específico, odoo_lint, verify, tres skills de dominio y casos de eval. Cubre XML, seguridad, ORM y preflight de MR.

PHP

PHP

Contrato, plantilla y rutas. PHPStan, PHPCS y PHPUnit todavía no están cableados; se presenta como esqueleto, no como terminado.

# ver y cambiar el perfil activo dev-agent profile list dev-agent profile use odoo11 # el perfil se copia; el config real no se versiona cat .dev-agent/config
Contrato: profile.json, profile.env, guard/, verify/, skills/, evals/ y AGENTS.fragment.md. Si no valida, no es instalable.
07 · Skills y agentes
una fuente, varias herramientas

La skill es procedimiento; el agente es el ejecutor.

Fuente neutral

skills/, commands/ y agents/ no dependen de Claude, OpenCode, Codex, pi ni Hermes.

Adaptadores

El proyecto genera .opencode/ y .claude/; las rutas globales reciben copias para Codex, pi y Hermes.

Regla

No se edita un adaptador a mano: se regenera. La fuente sigue siendo una.

Skill del núcleoCuándo se usaQué debe producir
dev-verifyDespués de un cambioEvidencia y veredicto, no una opinión.
repro-firstAl corregir un bugTest rojo antes del arreglo; después verde.
review-diffAntes de revisarHallazgos con severidad y veredicto.
correctCorrección repetidaLint, test o CI que impide que vuelva.
query-readonlyPregunta de datosConsulta de solo lectura y evidencia.
08 · Contexto
estructura y memoria

El agente no debería adivinar el repo ni olvidar la decisión.

CODEGRAPH

Estructura

Indexa ficheros, símbolos y llamadas. El agente consulta el mapa en vez de recorrer el árbol a ciegas.

# el instalador lo hace si está disponible codegraph init . codegraph sync . codegraph status .
ENGRAM

Memoria

Guarda decisiones, bugs y contexto del proyecto. La sesión termina; la memoria del proyecto no.

# guardar una decisión, sin secretos engram save "Decisión" \ "Qué se decidió y por qué" --type decision
Son apoyo: si faltan, el doctor lo dice. No sustituyen a guard, verify ni a la revisión.
09 · Norma de empresa
se enlaza, no se copia

tech-doc es la fuente canónica; el kit solo la conecta.

Qué se enlaza

scalpers-tech-doc/AGENTS.md se expone como ~/.agents/AGENTS.md. El kit y los perfiles añaden sus reglas, nunca reemplazan la norma.

Qué se comprueba

check-techdoc.sh verifica remoto, rama o commit, árbol limpio y enlace. Si el clon está sucio, falla cerrado.

# el instalador lo automatiza ./install.sh --with-techdoc # comprobación local bash scripts/check-techdoc.sh \ --path "$HOME/odoo-doodba-template/scalpers-tech-doc" \ --branch main --require-link
El HTML de tech-doc es privado, pesa varios MB y es un artefacto de build: se enlaza en local y nunca se copia al repo del kit.
10 · Ciclo de trabajo
de la rama al merge humano

Ocho pasos, siempre en el mismo orden.

1

Rama

feat/, fix/ o hotfix/; un cambio, un commit.

2

Contexto

AGENTS, perfil y, si aplica, CodeGraph y Engram.

3

Reproducir

Si es un bug, test rojo antes de tocar el código.

4

Implementar

Código, tests y documentación en el mismo cambio.

5

Guard

Sobre el cambio staged; sin perfil o sin datos, skipped.

6

Verify

Comportamiento real y evidencia; sin TEST_CMD, exit 2.

7

Revisión

Diff, evidencia y veredicto; la persona decide.

8

Entrega

CI y merge humano. El kit no despliega.

12 · Calidad de skills
medir el procedimiento, no el producto

Una skill se mejora cuando cambia el mecanismo que la demuestra.

Qué mide

  • Corridas K=3 por caso, en worktree o copia desechable.
  • Juez separado del ejecutor.
  • Media, mínimo, dispersión, tokens y coste.
  • Umbral de referencia 8,5.

Qué falta

  • OpenCode, Claude, Codex, pi y Hermes están soportados por el runner.
  • Codex necesita su propio login.
  • No es una puerta obligatoria hasta tener casos y medición.
  • Una skill inestable no se declara verde por una media alta.
python3 evals/harness.py \ --case-dir evals/cases/dev-verify/01-fix-failing-test \ --rubric evals/rubric.dev-verify.json \ --agent build \ --model <modelo-aprobado> \ --judge-model <modelo-aprobado-distinto> \ --k 3
13 · Seguridad
lo que el sistema no hace

La confianza no se automatiza; se comprueba.

Sin producción

El kit se instala en la base de desarrollo. No despliega ni configura servidores.

Sin secretos

No guarda tokens, claves ni contraseñas en el repo, la configuración o la evidencia.

Sin push

No hace push, merge ni release. Esas decisiones son humanas y del repo.

Sin borrados

Respalda con .bak-<fecha>. No borra datos, ramas ni historial.

El CI de Scalpers no se toca. El kit añade una puerta local; el CI y la revisión humana siguen siendo la garantía dura.
